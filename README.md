# WCM custody decisions as TRACE `authorized-intent` references (prototype)

A WCM key broker re-runs its release gate and signs a keyless decision,
`wcm-renewal/v1`. A TRACE Trust Record for the execution that followed can point
at that decision with a `references` entry, `rel: "authorized-intent"`. This
prototype shows the join working end to end and the cases where it must fail.

It follows the shape of two things already in trace-spec: the CHAP
`approval-outcome` example (a reference digest over the RFC 8785 form of an
external object, re-checked without importing the external system) and the
PIC/TRACE authorization bridge (the authorizer key comes from the verifier's
trust configuration, never from the object itself).

## What is joined

| Reference entry | Value |
|---|---|
| `rel` | `authorized-intent` |
| `id` | the decision's own identity: SHA-256 of the canonical signing payload (WCM `renewal_id`) |
| `digest` | SHA-256 of the canonical form of the whole stored decision, signature included |
| `resolver` | the party obliged to keep the decision resolvable |

| Fact checked | Against |
|---|---|
| decision signature | a broker key pinned by the relying party, not the key the decision carries |
| `renewed: true`, `kind: wcm-renewal/v1` | the decision is a release, not a denial |
| `weights_hash` | the record's `model.weights_digest` |
| `issued_at` to `expires_at` | an event time supplied by the relying party, evidenced separately: at or after `issued_at`, strictly before `expires_at` |
| `evidence_hash` | the attestation evidence, when the relying party holds it |

## Cases

| Record | Store | Verdict |
|---|---|---|
| `01-release-confirmed.json` | as issued | release-confirmed |
| `02-decision-altered-after-issue.json` | window stretched after issue | release-contradicted |
| `03-decision-is-a-denial.json` | as issued | not-a-release |
| `04-reference-unresolvable.json` | no such decision | release-unconfirmed |
| `05-execution-after-window.json` | as issued | outside-window |
| `06-different-weights.json` | as issued | different-weights |
| `07-unpinned-authorizer.json` | signed by an unpinned key | untrusted-authorizer |

The verdicts above are with the event time in `expected.json` supplied. The
records are issued a day after the window, and their `iat` is never taken as the
execution time: without a supplied event time, a valid decision gives
`authorized-execution-time-unestablished`.

Every record verifies as a TRACE record in every case. Section 3.1.2 rule 3: what
a reference resolves to never decides whether the record verifies. The verdict
answers a different question, what the referenced authorization establishes.

## One interoperability detail

WCM canonicalizes with null members omitted at every depth (a decision without
time-bounded revocation evidence carries `evidence_expires_at: null`). Plain
RFC 8785 over the stored object, nulls included, gives a different digest. A
profile has to say which form the digest is over. Here it is WCM's: RFC 8785
with nulls omitted. `test_digest_needs_null_members_omitted` pins this.

## A Custodian-format release receipt (synthetic)

Custodian implements shared custody. Each independent holder signs its grant. The
coordinator holds no model-key share and cannot authorize release alone. A release
needs grants from two distinct pinned holders. `custodian_check.py` checks a TRACE
`authorized-intent` reference to such a receipt, without importing WCM or
Custodian code. It is an independent example: it does not imply endorsement by
Custodian or a live production integration.

Every file in `fixtures/custodian/` is synthetic and generated by
`generate_custodian.py`: the holder keys are test keys derived from fixed bytes,
the quotes are labelled byte strings, and the measurements, manifest identity and
weights digest are hashes of labels. Nothing comes from a real deployment. The
fixtures cover the subset of the receipt that the holder-grant mapping uses; they
are not a complete export and carry no hardware appraisal. Never pin these keys
anywhere real.

The two reference entries are computed differently and serve different purposes:

| Reference entry | Purpose | Computed over |
|---|---|---|
| `id` | identity of the authorization, mapping `wcm-trace-custody/authorization-id/v1` | SHA-256 of the canonical JSON object `{"grant_envelopes": [...], "mapping": "wcm-trace-custody/authorization-id/v1"}`, where the list is the sorted SHA-256 digests of each grant envelope, each envelope being exactly `{payload, signature_hex}`. Canonical JSON here: sorted keys, compact separators, ASCII, nulls retained |
| `digest` | integrity of the stored receipt | SHA-256 of the exact stored file bytes, with no reserialization, so even a whitespace change changes it |

The id covers signed content only. It does not change with holder order, unsigned
row members or unsigned receipt metadata (the journal entry, the stated interval).
A grant envelope with any member besides `payload` and `signature_hex` is refused
as malformed.

| Fact checked | Against |
|---|---|
| trust pins | at least two holders with distinct valid Ed25519 keys, a threshold from 2 to the number of holders, the model scope, a positive local execution cap `max_seconds` |
| each grant's signature | the holder key pinned by the relying party, over `custodian:release-grant:v1\x00` plus the payload in the canonical JSON above |
| holders | every holder pinned, none repeated, at least `threshold` distinct |
| grant bindings | no two grants share a sealed-grant digest (`sealed_sha256`) or a holder challenge (`nonce`) |
| release | receipt and grant versions; every recorded gate passed |
| signed duration | each grant positive and no longer than its signed `max_seconds` and the holder's signed `grant_max_seconds` when present |
| `weights_hash`, `manifest_id` | the pins and the record's `model.weights_digest` |
| evidence | each grant's signed audit digests against the evidence, quote bytes and gate results carried in the receipt |
| runtime | one serving measurement and transport key across grants; optionally the relying party's runtime pin |
| window | intersection of the signed grant windows, nonempty; the receipt's stated interval must equal it |
| local execution cap | relying-party policy: each grant no longer than the pinned `max_seconds` |
| event time | supplied by the relying party, evidenced separately: at or after the start, strictly before expiry, full precision |

Authorization validity and local policy are reported separately. A shorter local
cap does not make a valid holder signature or its signed lifetime invalid: a valid
60-second grant under a 30-second local cap ends in `exceeds-local-cap`, with
`authorization_valid: true` and `local_policy_accepted: false`. A longer local cap
never extends a signed limit. The manifest's attestation cadence is not verified
here; that needs the manifest identity recomputed, which this check does not do.

Numbers must be interoperable JSON numbers (RFC 7493 section 2.2): finite
doubles, or integers from -(2^53 - 1) to 2^53 - 1. Input problems end in a verdict:
`invalid-arguments` for an event time or runtime pin that is not a string,
`invalid-trust-configuration` for invalid pins, `malformed-reference` for a
reference whose `id` or `digest` is not a non-empty string (checked before the
receipt is looked up), and `malformed-receipt` for a receipt that is not the
expected structure. `test_no_input_raises` feeds 4,000 randomly damaged records,
pins and receipts through the check, and none raises.

The records are retrospective imports, so they carry `origin.kind: "log-import"`
and `runtime.platform: "software-only"`, as TRACE 3.1.1 requires. Their `iat` is
when the record was issued, not when anything executed, and is never taken as the
execution time. Neither is any journal time carried in the receipt: it is
unsigned. Neither TRACE `iat` nor a coordinator journal timestamp proves when an
inference executed. Without a separately evidenced event time the verdict is
`authorized-execution-time-unestablished`: the authorization holds, when the
execution happened is not established. A supplied in-window time tests the
comparison; it does not prove an execution.

| Record | Receipt returned | Verdict |
|---|---|---|
| `08-custodian-authorized.json` | as issued | authorized-execution-time-unestablished |
| `09-custodian-grant-altered-after-issue.json` | customer grant expiry stretched | release-contradicted |
| `10-custodian-missing-holder.json` | one holder only | quorum-not-met |

| `12-custodian-unpinned-holder.json` | a grant from a holder no pin trusts | untrusted-authorizer |
| `13-custodian-different-weights.json` | as issued, record names other weights | different-weights |
| `14-custodian-evidence-altered.json` | evidence changed after signing | different-evidence |

| `16-custodian-exceeds-signed-limit.json` | grants signed for 660 s, signed maximum 60 s | exceeds-signed-limit |

The local cap, reference and argument cases are tests against these fixtures with
different pins or inputs, not separate records. Every record verifies as a TRACE
record in every case.

## Run

```
python -m pip install --require-hashes --no-deps -r requirements.txt
python -m pytest -q test_fixtures.py test_custodian.py
python generate_custodian.py fixtures/custodian   # byte-for-byte reproducible
```

The WCM-side fixtures were generated with the WCM SDK 0.33.1 and its example
manifest, `python/examples/manifest.example.json` at tag `v0.33.1` of the WCM
repository (SHA-256 `999e9cc807d0fa0d67b88971538a31ec7bad82654306433e458addc74ee203d9`,
checked by the generator):

```
python -m pip install --require-hashes --no-deps -r requirements-generate.txt
python generate.py fixtures path/to/manifest.example.json
```

The WCM SDK draws fresh keys and nonces on every run, so `generate.py` gives
different bytes each time and the same verdicts. The Custodian-format generator
uses fixed test keys and is reproducible exactly.

`requirements.txt` pins every dependency of the checks and tests with hashes,
`requirements-generate.txt` adds the WCM SDK for `generate.py`. The workflow in
`.github/workflows/test.yml` installs the pins and runs the tests and the
regeneration check on Linux with Python 3.12 and 3.13.

`check.py`, `custodian_check.py` and the tests do not import WCM or Custodian code.
Each verdict rule and input check was mutated out in turn and the suite failed
every time. The two catch-all exception handlers are the exception: with either
removed, no test and no fuzz input raises, because the explicit checks already
cover every input reached. They stay as a second line.

## Limits

- Evidence is WCM's `SoftwareProvider` mock: no hardware root of trust. The point is
  the reference, not the attestation.
- In the WCM reference SDK only the renewal decision is signed. In Custodian each
  holder signs its own grant for the release; the Custodian-format cases reference
  such a receipt, built synthetically.
- The Custodian-format check does not reappraise the hardware quote, its
  certificate chain or revocation, and does not recompute the manifest identity
  from an embedded manifest: it compares the signed `manifest_id` with the pin, and
  does not verify the manifest's attestation cadence. It
  verifies a historical authorization. It does not prove that an inference ran or
  that a runtime stopped, and it is not a live integration between a broker and a
  TRACE producer.
- Which party is the `resolver` is a deployment choice. Naming each holder for its
  own grant, or the operator for an exported receipt, keeps the record checkable
  without the broker or the coordinator.
